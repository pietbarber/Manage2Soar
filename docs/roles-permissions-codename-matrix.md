# Application authorization migration matrix (proposal)

> **Status: planning snapshot, not a current access contract.** Some rows were
> drafted before this branch introduced capability checks. Verify every
> “current checks” cell against the implementation and the
> [authorization inventory](roles-and-permissions-authorization-inventory.md)
> before using it for migration. Proposed codenames are not necessarily
> implemented or approved. CMS is covered separately in the
> [CMS baseline](cms-authorization-baseline.md).

## Reading rules

- “Current allow” is the legacy baseline at drafting time, not an exhaustive
  description of the branch; `superuser` means an explicit `is_superuser`
  branch, not merely staff.
- A route protected by `active_member_required` permits an authenticated kiosk
  session regardless of membership status (`members/decorators.py`), unless it
  uses `non_kiosk_member_required`.
- Proposed codenames are **not approved**. They should be added as explicit
  custom `Meta.permissions` only after the owner/context and parity tests below
  exist. `view/add/change/delete_*` entries are Django model CRUD permissions;
  `can_*` entries are business actions and must not be treated as CRUD.
- The proposed resolver should call `members.authorization.resolve_authorization`
  for the global permission, then apply the row’s contextual predicate. It must
  receive a fresh user when direct/group grants may have changed; the
  qualification backend intentionally evaluates current qualification grants.

## Permission vocabulary

| Kind | Meaning | Resolver context that must remain outside the codename |
|---|---|---|
| Model CRUD | Django `app_label.add/change/delete/view_model` | Object/queryset scope, finalized/closed state, ownership, and field visibility |
| Business action | Proposed `app_label.can_*` permission | Exact route action, target object, role/assignment, date/site, kiosk policy, and audit actor |
| Qualification-derived action | A `can_*` permission granted by an approved qualification bundle | Active member, current/non-obsolete/non-expired qualification, bundle safety rules, and target context |

## Cross-cutting parity risks and migration gates

1. **Legacy role flags are not equivalent to groups or permissions.** Current
   code mixes `is_superuser`, `is_staff`, `director`, `member_manager`,
   `rostermeister`, `treasurer`, `webmaster`, `safety_officer`, `stats_monger`,
   `instructor`, and named groups. Build an explicit role-to-permission mapping
   and test users having exactly one source before removing any flag branch.
2. **Kiosk is a principal/context, not a role.** `active_member_required`
   intentionally bypasses membership status for a kiosk session, while
   `non_kiosk_member_required` rejects it. Each proposed action must explicitly
   say whether kiosk is allowed; never infer it from `has_perm`.
3. **Ownership and state remain contextual.** Django global permissions do not
   enforce self/recipient/requester ownership, assignment role, finalization,
   billing-period closure, date windows, object aircraft, or application status.
4. **Qualification grants are capability grants only.** The backend excludes
   qualification admin permissions, member/role-management models, and standard
   CRUD/unsafe prefixes. New qualification-derived codenames should therefore
   be narrow `can_*` actions and pass the same safety denylist.
5. **Denial parity must include response shape.** Existing behavior varies
   between login redirects, 403 templates, `PermissionDenied`, JSON 403/400,
   and redirects with messages. Migration tests should assert status and
   side-effect absence, not only a boolean decision.
6. **Do not grant broad CRUD as a shortcut.** In particular, approval,
   unfinalization, exports/downloads, safety review, roster generation, and
   role assignment are business actions even where a model `change_*` currently
   exists.

## Suggested implementation/test sequence (no behavior change in this document)

1. Add resolver-level contract tests for unauthenticated, inactive, active,
   superuser, kiosk, legacy-flag, named-group, direct-permission, and
   qualification-derived principals.
2. Add route parity tests for every row above, including GET/POST/HTMX/JSON
   variants and object-ID substitution. Capture current expected responses first.
3. Introduce custom permissions and dual-check them behind instrumentation;
   compare decisions with the legacy predicate without changing the outcome.
4. Migrate one bounded surface at a time, retaining contextual predicates and
   audit fields. Only after parity evidence should legacy checks be retired.
5. Verify group/permission migrations on a fresh database and an existing
   database; no migration should rely on hard-coded permission or group PKs.
